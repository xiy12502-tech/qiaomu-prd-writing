# PRD 标准与分层结构

## 1. 文档首先服务于决策与协作

PRD 不是功能仓库，也不是技术设计。它应回答两类问题：

1. 管理层：为什么现在做、为谁做、带来什么价值、投入边界是什么、主要风险和待决策事项是什么？
2. 产品/设计/研发：用户如何完成任务、系统应表现为什么、范围在哪里、异常如何处理、怎样算完成？

默认使用同一份文档：第一页式“管理层决策摘要”在前，跨职能正文在后。这样避免摘要与正文成为两套真相。

## 2. 产品判断链

写功能前，先验证以下因果链：

`环境变化或机会（Why now） → 特定用户的具体问题 → 用户/业务价值 → 可衡量目标 → 最小有效方案 → 明确取舍`

若任何一环只有猜测，标为假设并提出验证方式。没有 Why now 时，可以写“当前触发因素尚未确认”，不要杜撰紧迫性。

## 3. 文档档位

### Lean

适用：单一角色、小范围、低风险、依赖少、无需正式立项或跨部门拍板。

最低内容：决策摘要；问题与用户；目标/成功标准；范围/非范围；核心流程或功能；验收标准；风险与待确认。

### Standard

适用：管理层评审、跨产品/设计/研发协作、多角色或多状态、涉及权限/数据/外部依赖、上线风险较高。

除 Lean 内容外，补充功能地图、详细需求、规则与状态、异常与恢复、权限、发布与衡量、决策记录。

若无法判断，默认 Standard，但允许将低价值章节标为“不适用”并说明原因，不为凑模板制造内容。

## 4. 管理层决策摘要

控制在快速阅读范围内，至少回答：

- 一句话结论与文档状态；
- 问题、Why now 与证据强度；
- 目标用户和核心场景；
- 用户价值与业务价值；
- 目标、成功信号和不追求什么；
- 推荐方案、备选方案、范围/非范围及关键取舍；
- 已知投入/影响范围；未知时明确待确认，不自行承诺资源与工期；
- 主要风险、依赖和需上级拍板事项，包括选项、推荐与不决策的影响。

不要把详细功能表复制到摘要。摘要要呈现判断和取舍，而不是章节目录。

## 5. 功能梳理方法

### 5.1 先能力地图，后页面清单

按用户任务或业务能力分组，例如“发现 → 决策 → 提交 → 跟踪 → 恢复”，而不是先列首页、按钮和弹窗。每组注明：

- 服务的用户任务；
- 优先级（Must / Should / Could / Won't for now）；
- 前置依赖；
- 成功结果；
- 明确排除项。

### 5.2 功能需求条目

Standard 模式使用稳定编号。推荐结构：

```markdown
### FR-001 功能名称

- 用户价值：
- 触发/前置条件：
- 预期行为与业务规则：
- 状态与异常：
- 权限/角色差异：
- 可验证结果：
- 不包含：
```

不要使用“体验友好、支持灵活配置、快速完成”等不可验证措辞；若保留，必须给出观察方式或阈值，并说明阈值来源。

### 5.3 核心流程

围绕用户目标描述起点、关键决策、成功终点和失败后的恢复。流程复杂且跨三方以上时可使用 Mermaid；同时保留文字版步骤。

### 5.4 状态、异常与权限

至少检查：首次/空状态、加载、成功、失败、部分成功、重复提交、超时、撤销/回退、无权限、数据冲突、跨端或中断恢复。只保留与当前产品有关的项。

## 6. 成功标准与验收标准

成功标准回答“产品是否创造了预期价值”，验收标准回答“需求是否按约定工作”。二者不能混用。

- 成功标准：结果指标、先行信号、观察窗口、基线/目标值和口径。未知时写 `【待确认】`，不要自行给数字。
- 验收标准：以可观察行为描述输入、条件、结果与失败处理。可以用 Given/When/Then，但不强制。

## 7. 条件章节

仅在相关时添加：法规与合规、数据与隐私、非功能要求、国际化/无障碍、商业化、迁移策略、竞品证据、埋点方案、术语表。未证实的市场与竞品信息必须标明来源或证据缺失。
